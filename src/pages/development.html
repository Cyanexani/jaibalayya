The stack

Six layers.
No magic.

Each layer only talks to the one below it. That constraint is the reason a contributor can replace the theme engine without knowing anything about notifications.

Core

Process lifecycle, the back stack, input routing and the launcher contract with Android.

UI engine

The Metro primitives: panorama, pivot, tile grid, the type ramp and the motion curves everything else animates with.

ui/ · Compose

Live Tile engine

One scheduler for every tile on the device: wake, render, sleep. Apps declare an update budget; the engine enforces it.

tiles/ · WorkManager

Theme engine

Accent, light/dark, density and typography as tokens, exposed to third-party apps through a content provider.

System services

App framework

Get it running

Build it
locally.

JDK 17, Android SDK 34, and a device or emulator on API 30+. That is the whole list.

build 
git clone https://github.com/metro-os/metro-os
cd metro-os

# debug build, straight onto a connected device
./gradlew :shell:installDebug

# one module at a time while you work
./gradlew :tiles:test :ui:test

# the checks CI runs before a review
./gradlew check lint

Write a tile

A live tile is one service.

Declare an update budget; return content when the engine asks. It decides when, so a hundred tiles cost what one would.

TileProvider.kt
class WeatherTile : TileProvider() {

  override val budget = UpdateBudget.EVERY_30_MIN

  override suspend fun render(size: TileSize) = tile {
    accent(Theme.accent)
    when (size) {
      TileSize.SMALL  -> icon("cloud")
      TileSize.MEDIUM -> { big("27°"); label("weather") }
      TileSize.WIDE   -> { big("27°"); text("Mostly clear") }
    }
    back { text("Thu 29°  ·  Fri 24°") }   // the flip face
  }
}
AndroidManifest.xml
<service android:name=".WeatherTile"
         android:exported="true">
  <intent-filter>
    <action android:name="os.metro.tiles.PROVIDE"/>
  </intent-filter>
</service>

Community

How decisions get made

  • Anything that changes behaviour across modules starts as an RFC in docs/rfcs.
  • Two maintainer approvals to merge into main; one for documentation.
  • Disagreements are settled in the issue, in public, and written down afterwards.
  • Nobody is paid, so nobody is owed a review deadline — but stale PRs get picked up at the weekly triage.

House rules

  • No telemetry, ever. Not opt-in, not anonymised, not “just for crashes”.
  • No Microsoft assets, names or icons in the source tree or in builds.
  • Accessibility is not a follow-up ticket: contrast, focus and reduced-motion ship with the feature.
  • If a change makes the shell slower, it needs a number explaining why that is acceptable.
